# refactor.md — what eleven folders of `src/` would change about themselves

Produced by `lore propose` on 2026-08-07 against commit `7325f08`, one full cycle per
folder: four lenses — data, failure, seams, greenfield — each with a proposer
(`openai/gpt-5.6-terra`) and a critic from a different vendor (`zai-coding-plan/glm-5-turbo`).
88 model sessions, 11 folders, four at a time.

**These are ideas, not findings.** Nothing here gates anything, nothing has been
implemented, and nothing has been reviewed. A person decides; anything taken goes
through the ladder like any other change (`spec/propose.md` §8). Every proposal keeps
the folder's behaviour — that is the `preserves` field, and it is what separates this
from a redesign.

**Read `Settled by` first, before the idea.** It is the one measurement that would show
the proposal is wrong, and reading it first is the whole defence against being
persuaded by three frontier models writing well. A proposal without one is in
*Unappraisable*, kept and ranked last rather than dropped.

### 4. failure — src/reviewer/review.ts

**Settled by:** Write a single test in round.test.ts that monkey-patches `store.db.exec` to throw after the Nth write (using a counter), runs a scripted round to completion, then reopens the same `:memory:` database (or uses a file-backed one), and asserts that the review state is either exactly the pre-round state (rollback worked) or exactly the completed-round state (commit happened before the throw) — never a mix of recorded findings without ladder advancement. This is a standard crash-injection test and decides the question in under an hour.

**Preserves:** All existing round.test.ts tests must pass unmodified because the transaction wraps the same writes in the same order — it only changes atomicity, not what is written or when. The recovery path via `reclaimOrphanedJobs` still fires at startup but now sees the job as `done` (the transaction committed before the crash) rather than `running`, so it correctly does nothing. The D-72 retry-after-crash behavior is preserved: a crash during the model call (before the transaction) still leaves the tier_run open and the job `running`, and requeue still re-runs it. Verify by running the full test suite.

Wrap the post-model persistence in `runRound` — the block from `recordUsage` through `updateReview` at the end of the success path — in a single `store.tx()` call so that findings, verdicts, knowledge, ladder state, tree hash, usage, and the review's state transition are committed atomically or not at all. The proposer is right that these writes are currently independent and that a crash between them leaves a partially-advanced ledger, but wrong about where the seam is and what it costs. The change belongs in `src/reviewer/review.ts`, not `src/core/ladder.ts` — ladder.ts is already pure and stateless by deliberate architectural contract ('Pure core, effectful edges'), and making it own persistence would be the exact inversion of that rule. The store already has `tx()` and it already works. What is missing is the caller wrapping the right span. The tier_run rows (opened before the model call and closed immediately after) must stay outside this transaction because they serve a different purpose — they are the 'is this tier still working?' signal a reader needs mid-flight, and they are already correctly closed on every path before the finalization block runs. The proposer also omits that `runRound` is async and `store.tx` is synchronous, so the commit payload must be assembled in a synchronous callback — the async work (scope reads, tree hash, file I/O) stays above it, and only the SQLite writes go inside. The proposal's `contradictedBy` citing D-72 is correct and well-stated: this must not retain an unverified model response. The transaction fires only after the response exists and is processed.

- **True if:** A process crash after the model returns but before all persistence completes can currently leave the database in a state where, say, findings are recorded but the ladder state was not advanced — so on restart, `reclaimOrphanedJobs` requeues the round, the ladder re-runs, and findings already on file are re-raised as duplicates, verdicts from the lost round are missing, and knowledge derived from accepted justifications in that round was never written. The audit trail describes a result the ladder never committed.
- **Costs, if wrong:** A focused test that injects a crash after each persistence call inside the proposed transaction boundary, reopens the database, and asserts only pre-round or post-round states — a few hours to write and run, and entirely revertible because it adds a `store.tx()` call around existing writes. The real risk is getting the boundary wrong: wrapping too little leaves the same hole; wrapping the tier_run closes would defer the 'tier is working' signal behind the same commit, making a reader unable to distinguish a tier that died from one that just hasn't committed yet — which is exactly the INV-1 shape the open/close-before-commit design exists to prevent. A second risk is that the synchronous `tx()` callback implicitly batches writes that were previously separated by async boundaries, and any of those async operations (file reads for scope, tree hash computation) throwing inside the callback would trigger a rollback of writes that previously succeeded on their own — a silent regression from 'partial state' to 'no state at all'.
- **Argued against by:** The core architecture rule stated in CLAUDE.md and README.md: 'Pure core, effectful edges. Diff parsing, fingerprinting, dedup, ledger reconciliation and the escalation state machine are pure functions over plain data — they are the parts that must be testable without a model, a network, or a repo.' The proposer lists `src/core/ladder.ts` as a touch target, but ladder.ts is the pure reducer — it takes a `StepInput` and returns a `{state, decision}` pair, touching no database. Making it own transactional persistence would invert the architecture. The change belongs in `review.ts`, the effectful edge that already calls store methods. Additionally, the existing `reclaimOrphanedJobs` at startup already handles the crash-during-round case by requeuing the job, which is the designed recovery path (D-72) — the proposal must coexist with that, not replace it. A transaction that commits the round outcome means the requeue path must check whether the round actually completed before re-running, which is new logic the proposal does not mention.
- **out-of-scope:** lands in src/reviewer/review.ts, none of it inside src/core

### src/git — 1. data — src/git/repo.ts, src/mcp/server.ts, src/git/apply.test.ts

**Settled by:** One test: apply a valid two-file diff to a worktree whose `treeHash` is captured first, pass a `tree_hash` that does not match the result, catch the mismatch error, then hash the worktree again — it must equal the pre-apply hash. Run it in `src/git/apply.test.ts` which already has the `mkdtempSync`+`git init` fixture. This decides the mechanism but not the contract ambiguity — that needs a spec sentence.

**Preserves:** A successful submit produces the same tree hash, sets the review to queued, and enqueues fast exactly as before — the rollback is on the error path only, which today leaves a dirty worktree. A failed `applyPatch` (git rejects the diff) is untouched — the worktree is already clean and the test at apply.test.ts:99 proves it. The mismatch error message can keep its 'Re-send' instruction because it will now be truthful: the worktree really is back at the base the client's diff was computed from.

When `review_submit` applies a diff and the resulting tree hash does not match the client's `tree_hash`, the worktree has been mutated but the review row still records the old tree — and the error message tells the client to resend the full diff against the original base, which no longer exists. The fix is a `resetWorktree` function in `src/git/repo.ts` that discards all uncommitted changes (working tree and index) back to HEAD, called in the mismatch catch block in `src/mcp/server.ts` before the error is thrown. The success path is untouched. The `applyPatch` failure path is untouched — `git apply` already rejects atomically and the test proves the worktree is unchanged. This only closes the gap where `applyPatch` succeeds (possibly fuzzily, thanks to `--recount`) but the hash disagrees, leaving the worktree in an unrecorded state that makes the retry instruction a lie.

- **True if:** A tree-hash mismatch is recoverable by resending the full intended diff, as the error text instructs, rather than being a one-way door that poisons the worktree for all subsequent submits on that review.
- **Costs, if wrong:** A `git checkout -- . && git reset` wrapper — under ten lines in repo.ts and a call site in server.ts. One new test case in apply.test.ts that applies a valid diff, hashes, confirms mismatch, calls the reset, and asserts the worktree files and index are back at HEAD. The rollback mechanism itself (`git restore --staged --worktree .`) is standard git with no lore-specific risk; the worst it can do on failure is leave the worktree dirty, which is the state that already exists today. If the reset itself throws, the original mismatch error should still be thrown — the caller asked for an atomic operation and both outcomes (clean rollback or original error) are acceptable; a rollback failure wrapping the mismatch is not.
- **Argued against by:** MEMO.md line 2016 says 'mismatch is terminal', and spec/mcp-api.md §4 says 'A mismatch is a hard failure, never a warning'. If 'terminal' means the review itself must fail rather than the submit attempt, then rolling back and accepting a retry contradicts the spec. The error message on line 567 of server.ts says 'Re-send the full diff for the tree you actually have', which contradicts 'terminal'. The proposal correctly identifies this tension but resolves it by following the error text over MEMO.md — the right call, but the ambiguity in MEMO.md should be settled explicitly in the same change, not left for the next reader to reinterpret. The spec should say what mismatch means for the review state (nothing — the review stays in findings_ready/awaiting_diff) versus what it means for the submit (rejected, worktree restored, retry is valid).

### src/git — 2. failure — src/git/repo.ts

**Settled by:** In a real bare repository with a registered worktree, make `git worktree remove` fail (e.g. by locking the bare repo's filesystem or killing the git process), call `removeWorktree`, and check two things: (1) does the directory still exist, and (2) does `git worktree list --porcelain` still show the entry. If the directory vanishes, the change prevents a real leak. If the entry vanishes too (git cleaned its own record before failing), the fallback is needed and this proposal makes cleanup worse. The proposer's own measurement is correct — this is the test — but it must verify BOTH conditions, not just the directory.

**Preserves:** For a valid registered worktree where git succeeds (the normal case), cleanup must still remove both the directory and the Git record. The existing retention test ('releases git's bookkeeping, not just the directory') is the regression guard. The propose CLI's `finally`-block cleanup must not crash the process after output is written — a thrown error there is a behavioural change. The retention sweep must not abort over one stuck worktree — a thrown error there is a behavioural change. Both callers would need explicit catch sites, and neither is mentioned in the proposal.

Stop `removeWorktree` from falling back to a bare `rm -rf` when `git worktree remove --force` fails. Currently the function swallows the git error with `.catch(() => undefined)` and unconditionally deletes the directory anyway, which is the exact leak D-70 forbids: git's administrative record under `bare.git/worktrees/<id>` survives while the directory vanishes, so `git worktree list` names paths that are not there. The change: let the git failure propagate (or return a distinguishable failure) so callers can alert or retry while Git's bookkeeping and the directory stay consistent. The proposer omitted the three callers and what each one does with the failure today — and that is where the real argument lives. `releaseIfFinished` in worker.ts (line 248) already catches and logs; it would need to absorb the new throw, but the alert already fires on failure, so nothing changes except the directory stays on disk until retry/sweep. `collect` in retention.ts (line 103) maps failure to `false` via `.then(() => true, () => false)` and continues the loop; a thrown error would abort the entire sweep over one stuck worktree unless the catch is added at that site. The propose CLI (line 142) swallows all errors with `.catch(() => undefined)` in a `finally` block — a thrown error there would crash the CLI after producing its output document. Each caller needs its own handling of the new failure mode, and the proposer listed none of them.

- **True if:** A failed `git worktree remove` leaves Git's administrative record intact while `rm -rf` silently deletes the directory beneath it — producing the orphaned-record state D-70 measured and SPEC forbids. If git always either succeeds or removes its own record on failure, the fallback is harmless. If git removes its record but leaves the directory, the fallback is necessary and this change is wrong.
- **Costs, if wrong:** The proposer estimated 'noisier cleanup' and that is the optimistic reading. The real cost: `releaseIfFinished` already swallows the error — it would need to be changed to catch the new throw. `collect` would abort the hourly sweep on the first stuck worktree, leaving every other finished review's worktree on disk until the next hourly pass, on a system whose disk hit 88% before D-70 was implemented. The propose CLI would crash after writing its output in a `finally` block. If git worktree remove fails because the bare repository is temporarily unresponsive (a busy SQLite lock from the service itself, or filesystem contention on the Orange Pi), every finished review piles up until the lock clears — and the system already has one documented incident where a SQLite lock across a VM boundary corrupted the live database. Making cleanup synchronous and failure-blocking against a git operation that can fail for transient reasons is the opposite of what D-70's backstop design intended.
- **Argued against by:** Three things. First, D-70 and `spec/operations.md` §5 say 'release goes through git worktree remove, never a bare rm' — which the proposer reads as 'never rm if git fails', but the spec's actual text is about ordering (git first), and `pruneWorktrees` exists precisely to collect the records git cannot reach, acknowledging that the git-first path does leave garbage sometimes. Second, the proposer's own `contradictedBy` says 'removeWorktree and its callers currently deliberately make cleanup best-effort and non-fatal' — and that is not a contradiction, it is the design. `releaseIfFinished` (line 238-239) says 'Never fatal. A worktree that cannot be removed is a disk problem to report, not a reason to fail a review that has already finished.' Third, the proposer listed `src/git/escape.test.ts` as a touched file but it tests `ensureBare` and `worktreeFor`, not `removeWorktree` — nothing in that file needs to change for this proposal.

A half-written tree producing false tsc/eslint findings is the exact failure deployment.md §3.1 documents, and the spec's claim that 'installs sharing a cache directory are serialised' fixes it is incomplete — it serialises the writes but not the read-after-write. However, the proposer does not consider the obvious narrower fix: extend the lock scope inside `sandboxed()` to cover `checkTypes` and `checkLint` as well as `install`. That would serialise the full lifecycle per lockfile key with near-zero throughput cost — the warm install is ~200ms measured, and adding a ~2s check to the lock hold simply means same-lockfile reviews run one at a time through T0, which is what they already effectively do since the concurrency is bounded by CPU cores. Per-review materialization trades a real but narrow race window for guaranteed cold installs on every same-lockfile review, which is precisely the wall-clock cost D-37 measured and the shared cache was built to avoid. The proposer also omits that the install container runs with network access and lifecycle scripts enabled — per-review installs multiply that surface rather than sharing one already-written tree.

- **True if:** Two T0 runs can overlap for worktrees sharing the same lockfile cache key, and the second run's install mutates the shared node_modules directory while the first run's tsc or eslint container is reading from it. This is true by code inspection: `withInstallLock` on line 165 wraps only `install()`, and `checkTypes`/`checkLint` on lines 197–198 run after the lock releases, against the same `cacheDir` bind mount.
- **Costs, if wrong:** If the simpler lock-scope extension would have sufficed and we went with per-review materialization instead, every same-lockfile review pays a cold install (seconds on ARM, minutes for large monorepos) instead of reusing a warm cache at ~200ms. At 30 PRs/day × 5 rounds on modest ARM cores, that is the bottleneck D-37 measured, made worse. Disk usage grows proportionally to concurrent reviews of the same repo. The package-manager download cache mitigates network cost but not the CPU cost of resolution and file linking. If the race turns out never to manifest in production — the window is a 200ms install overlapping a ~2s check of the same lockfile — the entire refactor is pure cost with no benefit. The proposer's own `costIfWrong` understates this by calling it 'higher cold-install and disk cost' when the deployment spec's entire T0 throughput argument is built on avoiding exactly that cost.
- **Argued against by:** D-37 and `spec/deployment.md` §3 table row 1 ('node_modules cache keyed by lockfile hash — a fresh install per review would dominate everything') explicitly choose the shared cache to save CPU on a host where disk is plentiful and CPU is scarce. The spec's claim in §3.1 that 'installs sharing a cache directory are serialised' as the fix is incomplete rather than contradicting the proposal — it identifies the right failure mode but stops at serialising writes, not reads. The design intent is clear: reuse the cached tree. The proposal abandons that intent rather than patching the gap. Additionally, the `withInstallLock` comment at lines 47–51 explicitly documents that this is in-process only and that a second lore process on the same data directory would need a file lock — per-review materialization does not fix that limitation either, since two processes could still race on the same per-review directory.

Measured: a warm install is ~200ms and typecheck ~2s for this repo (deployment.md §3), so the queueing cost per overlapping review is the sum of those phases rather than just the install. For a large monorepo whose typecheck takes 30s, two concurrent reviews of the same repo would go from ~30s wall-clock (parallel) to ~60s (serial). The proposer's own `costIfWrong` already names this. The real risk is subtler: the proposer did not check whether `checkTypes`/`checkLint` mount `node_modules` as read-write (they do, line 122), which means the checkers themselves could theoretically race with each other even if the install were perfectly ordered.
